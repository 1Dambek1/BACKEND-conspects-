# Кэширование в Redis — список пицц в FastAPI

Представь, что 20 человек подряд открыли меню. Пиццы и цены за это время не изменились. Первый запрос может прочитать меню из базы и на минуту оставить копию в Redis. Следующие запросы получат эту копию. База остаётся источником данных, а Redis хранит **кэш** — результат, который можно собрать заново.

## Два пути для одного запроса

| Что нашёл `await r.get("pizzas_cache")` | Что делает `GET /pizzas` |
| --- | --- |
| `None`: копии нет (**MISS**) | Читает пиццы из базы, записывает список в Redis на 60 секунд, возвращает список |
| Строку JSON: копия есть (**HIT**) | Превращает строку обратно в список и возвращает его без `SELECT` |

Такой порядок называют **cache-aside**: приложение само решает, когда читать базу и заполнять кэш. `ex=60` задаёт **TTL** — срок жизни ключа в секундах. Обычный `GET` этот срок не продлевает. Когда время истечёт, список заново соберёт следующий запрос к меню. [Команда SET с параметром EX](https://redis.io/docs/latest/commands/set/).

## Обработчик FastAPI

В исходном примере `return time.time() - times` возвращает число секунд. Для проверки скорости это удобно, но посетитель меню ждёт список пицц. Вернём список в теле ответа, а время работы обработчика и источник данных положим в заголовки.

Ниже используются уже существующие в проекте `app`, модель `Pizza` и зависимость `get_session`. Для асинхронного Redis-клиента нужен пакет `redis` (`python -m pip install redis`).

```python
import json
import os
from time import perf_counter

from fastapi import Depends, Response
from redis.asyncio import Redis
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

r = Redis.from_url(
    os.getenv("CACHE_REDIS_URL", "redis://localhost:6379/2"),
    decode_responses=True,
)
MENU_KEY = "pizzas_cache"


@app.get("/pizzas")
async def get_pizzas(response: Response, session: AsyncSession = Depends(get_session)):
    start = perf_counter()
    cached = await r.get(MENU_KEY)

    if cached is None:
        pizzas = (await session.scalars(select(Pizza).order_by(Pizza.id))).all()
        data = [
            {"id": p.id, "name": p.name, "price": p.price, "description": p.description}
            for p in pizzas
        ]
        await r.set(MENU_KEY, json.dumps(data, ensure_ascii=False), ex=60)
        source = "MISS"
    else:
        data = json.loads(cached)
        source = "HIT"

    response.headers["X-Cache"] = source
    response.headers["X-Handler-Ms"] = f"{(perf_counter() - start) * 1000:.2f}"
    return data
```

`json.dumps()` записывает список словарей как JSON, а `json.loads()` восстанавливает список. Проверка `cached is None` означает именно «ключа нет». Если в меню пока нет пицц, сохранённая строка `"[]"` — полноценный ответ: второй запрос вернёт пустой список без обращения к таблице.

В примере цена — число, которое поддерживает JSON, например целое количество копеек. Если у модели `price` имеет тип `Decimal`, заранее выбери формат ответа: например, запиши `"price": str(p.price)` при составлении словаря. Тогда цена будет строкой в обеих ветках и `json.dumps()` сможет её сохранить.

Для приложения внутри [Docker Compose](<Docker Compose — запуск backend и сервисов.md>) задай `CACHE_REDIS_URL=redis://redis:6379/2`: там Redis доступен по имени сервиса. Клиент создают один раз на процесс, а при завершении приложения закрывают через `await r.aclose()` в `lifespan`. [Асинхронный клиент redis-py](https://redis.readthedocs.io/en/stable/examples/asyncio_examples.html).

## Что делать после изменения цены

Допустим, цена уже изменилась в базе, но в Redis ещё лежит прежнее меню. Чтобы покупатель не ждал окончания минуты, удаляй ключ после **успешного** сохранения изменений. Это называется **инвалидация кэша**.

```python
# Фрагмент обработчика изменения цены: pizza уже загружена из базы.
pizza.price = new_price
await session.commit()
await r.delete(MENU_KEY)
```

Так же поступай после добавления и удаления пиццы. Следующий `GET /pizzas` получит `MISS` и запишет обновлённое меню. Если удалить ключ до `commit()`, другой запрос может прочитать ещё не обновлённую цену и вернуть её в кэш. При одновременных чтениях и записях даже схема с удалением после коммита не гарантирует мгновенной согласованности: цену для оформления заказа проверяй по базе.

## Как увидеть разницу

Из терминала выполни дважды в течение минуты (в PowerShell можно использовать `curl.exe`):

```bash
curl -i http://127.0.0.1:8000/pizzas
```

Если ключа сначала не было, увидишь **MISS → HIT**. Тело ответа в обоих случаях одинаковое. Заголовок `X-Handler-Ms` показывает время работы кода обработчика; передача ответа по сети в него не входит. После обновления цены и удаления ключа ожидай снова **MISS → HIT**, уже с новой ценой.

Ключ `pizzas_cache` подходит, пока меню одно для всех. Если появится фильтр по городу, включи город в ключ (например, `pizzas:irkutsk`), иначе клиент может получить чужое меню. А если Redis недоступен, `get()` вызовет ошибку подключения. Чтобы меню продолжало работать при таком сбое, в приложении можно отдельно обработать ошибки соединения и таймаута Redis и прочитать данные из базы.
